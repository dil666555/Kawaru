# HPC 超时与资源回收策略

目标是让网络等待、上报、清理和退出都有边界，避免业务已经结束却继续占用计算资源。

以下明确各侧应保证的内容，表中时间为初始建议值。容器侧代码已接入，尚未进行运行验收；计算框架和后端侧需在各自仓库落实。

## 1. 容器侧要保证的内容

负责计算之外的网络、结果上报、清理和进程退出；四类任务统一接入。

| 环节 | 策略与初始建议值 |
| --- | --- |
| 下载、上传 | 按每个活跃请求的实际字节进度判断；连续 60 秒无进度则超时，首字节等待和传输完成后的响应等待也必须有界。其他请求有进度不能掩盖单个请求停滞；持续有进度的大文件可以继续传输。 |
| HEAD、分页列举、删除等小请求 | 每次请求最多 30 秒；正常分页遍历不设整体短时限。可重试的网络错误最多尝试 3 次，包含首次及 SDK 内部重试。 |
| manifest 与回调 | manifest 是记录业务结果的终态文件。上传预算 60 秒；回调预算 30 秒、最多两次；各自预算包含全部尝试和退避。 |
| 清理 | 失败后的 OSS 清理最多 120 秒，本地临时目录清理最多 60 秒；到期停止等待，遗留 OSS 清理由后端处理。 |
| 退出 | 主流程返回后最多等待 30 秒。独立监督进程负责结束仍存活的工作进程及子进程；先发送终止信号，10 秒后仍未结束则强杀。网络或收尾确定超时、收到取消信号时也由它处理。工作进程崩溃时，监督进程不能无限等完成通知，也不能伪造成功。 |

**成功顺序：完整上传输出 → 提交成功 manifest → 回调 → 本地清理 → 退出。** 回调、清理或退出卡住，不翻转已提交的成功结果，也不删除成功输出。输出完整但 manifest 提交无法确认时，保留输出，交给后端核对。

**删除安全：**校验输出路径非空、合法，且不包含输入或 manifest；发布前清空和失败清理都只允许操作本次执行独占的输出目录。清理前先确保所有相关工作进程及子进程已停止写入。UMAP 写回源 Zarr，失败时不能删除整个源前缀。目录独占还需后端保证，路径格式合法本身不能证明所有权。

**结果可核对：**manifest、回调和日志关联后端传入的本次执行标识（attempt），分别记录业务结果、上报状态和强制退出原因，不能把回调送达、业务成功和进程退出混为一件事。

**计算边界：**不设置作业总时限，不修改 MassFlow、算法或现有默认 600 秒停滞策略，不因日志沉默、CPU 低或文件未变化而杀计算。MassFlow 内部卡在无限 `join()` 的情况本方案仍无法自动回收。

## 2. 计算框架侧（MassFlow）要保证的内容

负责判断计算内部是否停滞，以及让计算正常结束或明确失败；相关修复在 MassFlow 仓库完成。

1. **停滞判断有真实依据。**现有默认 600 秒策略依据框架内部流水线活动；普通日志、定时心跳不能替代计算进展，也不对正常长计算或 finalize 额外设置总时限。
2. **异常和超时能够传出。**计算失败后，应向调用方返回异常或提供明确的失败通知，不能先卡在无限 `join()`，让容器一直以为仍在计算。
3. **内部收尾能够结束。**失败后停止继续调度，结束相关队列、线程和资源等待；无法自行回收时，需要把明确的终止依据交给容器监督进程，由它回收整个工作进程及子进程。
4. **成功只在结果完整后返回。**计算、合并和 finalize 完成后再报告成功，避免容器上传尚未写完的结果。

当前已知的无限 `join()` 缺口需要框架侧修复；修复及失败通知接入前，容器侧仍不承诺自动识别这类内部卡死。

## 3. 后端侧要保证的内容

以下属于调用方仓库的接入责任，本仓库提供镜像和结果契约。

1. **使用批处理模式。**任务主进程退出后，由平台自动释放执行节点；后台服务模式需要另外释放。拿到成功结果不等于资源已释放，要核对平台终态。[平台说明](https://www.alibabacloud.com/help/en/e-hpc/e-hpc-instant/user-guide/create-job)
2. **凭证有效期覆盖全过程。**STS 默认一小时指 OSS 访问凭证有效期，与容器寿命不同；从签发时开始计时，排队也占用有效期。后端可申请更长有效期，受 RAM 角色上限约束，最长十二小时。当前镜像不刷新凭证，更长任务需另行约定续期方案。[STS 说明](https://www.alibabacloud.com/help/en/ram/user-guide/assume-a-ram-role)
3. **记录每次执行并保证目录独占。**提交前生成并传入本次执行标识（attempt），记录业务 ID、JobId、输出和 manifest 位置；每次执行使用新的独占输出目录，不传公共父目录，不允许并发写同一 Zarr。提交响应丢失时先查询核对，不直接重提。manifest、回调和停止操作都要对应本次执行，防止旧结果影响新任务；确需复用输出路径时，须确认旧任务和旧清理均已结束。
4. **关闭整单自动重试，正确消费结果。**约定退出码：`0` 成功（收尾异常另记日志）；`2` 算法或发布失败；`3` 输出完整但 manifest 提交未确认，包括上传超时；`64` 配置错误；`124` 下载或数据上传等外层阶段超时导致业务未完成。`3` 需核对本次 manifest，不能直接重算或删除输出。OOM、平台强杀等情况也要检查重试策略，不能只处理 `124`。
5. **平台巡检只停止有明确依据的作业。**本次执行已有可信终态但超过收尾期限仍在运行，或用户明确取消时，才请求停止。终态后的期限要覆盖仍允许执行的回调、清理和退出预算，不能直接套用主流程返回后的 30 秒。不要按旧 FC 的固定时长、日志沉默或心跳丢失终止计算。停止后继续核对平台终态；本地轮询超时、数据库标失败都不代表作业已结束。
6. **接管遗留清理。**容器清理超时后，由后端根据本次执行记录继续处理。未完成的 Zarr 不能作为成功结果；成功输出、共享输入和 UMAP 源 Zarr 不得被误删。
